## What holds (checked at the source)
- **Kept apart from the regular session.** Own log file, own gates, own close; no `close_loops`, so an off-day run cannot trip the session-day guard and pause Instagram. `close` refuses any handle that is not in the day's plan and any non-sweep action.
- **Never re-followed.** Every unfollow lands in `unfollowed_history` with source `manual_sweep_2026_11`; aborted and done handles are skipped by the next plan.
- **Protections are real code, not runbook text:** follower lists of the last 12 days, the Half the Night send list until 12-21 (with Amir's 7 exceptions), personal network, keep_following, the protected set (all four names from memory are in it), blocked list, accounts no longer followed.
- **Fails closed.** No follower list in 2 days, an untrusted union, no picks copy, a pause, a detection cooldown, a wrong day or hour: each one stops the run with no clicks. A detection word in a halt sets pauses.ig.
- **Dry run writes nothing** (`cmd_plan` returns before any write when `--dry-run` is set).

## Fixes

1. **MUST: the run-day fetch will be refused by the 300/day cap on most run days.** The fetch needs 85 calls at 16:00. The dispatcher at 09:30 already uses 241 on a normal day (11-07, 11-08: audit 200 + re-enrich 40 + sync 1) and up to 300. 241 + 85 = 326 > 300, so the ledger refuses, the plan says BLOCKED and the run is lost. Run 1 is probably saved by luck: the dispatcher's own weekly list fetch is due Tue 11-17 09:30. Runs 3, 5 and 6 (11-22, 11-26, 11-29) need their own fetch. Fix in the IG chat: reserve 85 calls on the six run days (for example the audit takes 115 instead of 200 on those days), or Amir's yes for +85 on those days.
2. **MUST: this replaces a HARD rule and nothing records it.** Memory `ig-web-follows-you-badge-unreliable` says browser unfollows only with the All-time export. The sweep uses HikerAPI follower lists instead. Amir approved the sweep plan on 11-14, but the hard rule still says "export". Get his one-line confirmation that provider follower lists stand in for the export for this sweep, and add a dated line to that memory.
3. **SHOULD: a failed picks read silently uses an older copy.** The runbook says "a late flip to Keep must count", but when today's ArtifactData read fails the plan takes the newest saved copy, which can be days old. Stop the live run when today's copy is missing.
4. **SHOULD: a blocked plan file cannot be rebuilt.** A plan written with blocks (exit 3) is kept on the next call, and the runbook forbids `--rebuild`. So one refused fetch kills the day even if calls free up. Let `plan` replace a stored plan that has blocks and no clicks logged.

## Honest note on the follower check
- "combined 996 vs profile 993: TRUSTED" compares counts only. The union covers 12 days, so it also holds people who stopped following; an equal count does not prove every current follower is in it. Single fetches are partial (286, 787, 689, 876, 968 names), and a partial list fetched today still counts as "newest".
- So a few real followers can be missing from the union. For these picks (older follows, already cross-checked as non-followers) the chance is small, and the runbook's last guard catches it: a button that reads "Follow Back" after the click means re-follow at once and tell Amir.
- That guard is what makes this safe enough, not the count test. Every "Follow Back" re-follow must reach Amir in the run report (the runbook already says so).
