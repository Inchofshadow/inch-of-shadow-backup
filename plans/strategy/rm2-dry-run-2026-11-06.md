## 1. Target structure

### 1a. One app, six area modules

`webapp.py` becomes a thin file: it builds `app` from `release_manager/core.py`, imports the six
area modules so their routes register, and re-exports the names the tests import. Every route keeps
its endpoint name and its URL.

| Module | Nav group | Pages (after D17) | Routes | Helper modules it owns |
|---|---|---|---|---|
| `views/release.py` | Release | Home `/` (slice 10), `/release/*` (incl. the clip pack block S10), `/artwork-resizer` as a release tool (no nav entry) | 16 + 1 | models, storage, timeline, checklist, artwork_resizer (CLI) |
| `views/studio.py` (4 files: `studio.py` archive+effects+fonts+video, `shoot.py` shoot+edit, `imagine.py`, `playground.py`) | Studio | Shoot, Archive, Fonts, Effects, Cover (playground), Imagine, Video (+ Video Resizer merged), Photo editor | 76 | photo_edit, imagine*, video_resizer, shoot_catalogue, shoot_pull, edit_recipe, cover_fonts, fonts_page, playground, print_looks, effects_page, archive |
| `views/words.py` | Words | Words = SEO copy + Bios on one page | 13 | seo_copy_generator, bio_manager, writers_ai, brand_context, copy_pass |
| `views/work.py` | Work (Socials + System queue) | Work = Tickets + Board + By number, Outreach, Review (new), SC automation (if the SC chat keeps it) | 3 + 2 + 2 + 4 | tickets, board, outreach, review (new) |
| `views/stats.py` | Stats | Stats (M11 rebuild lands here later) | 10 | score_board, stats_tracks, `stats/*` |
| `core.py` (not a view) | | `favicon`, 404, `serve_artwork`, `serve_resized`, `serve_resized_video`, context processor, filters, CSRF, constants (`PROJECT_ROOT`, `SOCIAL_LINKS`, presets) | 5 | paths, storage |

**Why area modules and not Flask `Blueprint` objects.** A `Blueprint` prefixes every endpoint
(`stats.stats_page`). That would change 181 `url_for(...)` strings in templates, 49 in `webapp.py`,
and the 19 `request.endpoint == 'name'` checks that light the nav in `base.html` plus the one in
`_cover_steps.html`. Area modules that import `app` from `core.py` and decorate with `@app.route`
keep all of that untouched: zero template edits, zero test edits for the names. If Amir wants real
Blueprints later, the only safe way is `Blueprint` plus an `app.url_build_error_handlers` shim that
resolves bare names; that is a separate decision, not needed for RM 2.0. The word "blueprint" in the
page map means "area module" from here on.

**Import shape.** `core.py` holds `app`, CSRF, `inject_globals`, the three filters, `load_theme`,
`load_genres`, `find_artwork`, `artwork_url_for`, the storage re-exports and the constants. View
modules do `from release_manager.core import app, PROJECT_ROOT, list_releases, ...`. `webapp.py`
does `from release_manager.core import *` plus `import release_manager.views.release` (and the other
five) plus `from release_manager.views.release import _dashboard_lines, _make_block` and the other
names section 4 lists. `python -m release_manager.webapp` and `from release_manager.webapp import app`
keep working unchanged.

   `Blueprint` objects; then `base.html` alone needs about 50 edits and every template its strings.

   11 `from release_manager.webapp import app`, 4 `from release_manager import webapp`, and these
